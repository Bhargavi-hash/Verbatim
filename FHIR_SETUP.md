# FHIR Setup — Synthetic Patient Data

## Read this first: the Epic sandbox gotcha

Epic's public sandbox gives you **eight fixed test patients** (Camila Lopez, Derrick Lin,
and six others). You **cannot create your own patient there**, and write/POST access
requires a registered, approved app — which may not land inside a one-day build.

So this kit is built to work **two ways**, switched by one environment variable:

| Mode | Target | Why |
|---|---|---|
| `hapi` (**default — use for the demo**) | Public HAPI FHIR test server | Accepts POST immediately, no registration, no approval. Your demo cannot fail here. |
| `epic` (stretch goal) | Epic FHIR sandbox | The impressive version. Use a REAL Epic test patient ID; do not POST your own Patient. |

**Recommended play:** build and demo on `hapi`, and if Epic app registration comes
through during the day, flip the env var and show the Epic write as the bonus. Say this
out loud in the demo — judges respect a team that de-risked its critical path.

## Where the files go

Drop the `data/` folder into the root of your repo:

```
your-repo/
├── prompts/                              # PDD .prompt files (source of truth)
├── src/
│   └── fhir_writer.py                    # generated by: pdd --force sync fhir_writer
├── data/
│   ├── patients/
│   │   └── synthetic-maria-gonzalez.json # synthetic Patient (for hapi mode)
│   ├── fixtures/

│   │   └── sample_structured_intake.json # expected structurer output (use as a test fixture)
│   └── fhir/

├── README.md
└── PDD_EVIDENCE.md
```

## What each file is for

**`data/patients/synthetic-maria-gonzalez.json`** — a valid FHIR R4 `Patient`: 50-year-old
Spanish-preferred speaker, tagged `HTEST` (the standard "test data" marker, so nobody can
mistake it for real PHI). POST this once to HAPI to create your demo patient. **Skip this
in Epic mode** — use an existing sandbox patient instead.

**`data/fixtures/sample_conversation_es.json`** — an 11-turn Spanish intake conversation
(chest pain, 8/10, shortness of breath, left arm numbness). Two jobs: it's your test
fixture for the structurer, and it lets the team develop **without spending ElevenLabs
credits** on every run.

**`data/fixtures/sample_structured_intake.json`** — the expected structurer output for that
conversation. This is your **fidelity showcase**: every field carries `source_span`,
`source_turn`, and `stated_by_patient`. Note "Hypertension" is marked
`stated_by_patient: false` — inferred from the medication, not said by the patient. That
one field is the most compelling thing in your entire demo. Point at it.

**`data/fhir/intake_bundle_template.json`** — a FHIR `transaction` Bundle with Encounter,
pain-severity Observation (LOINC 72514-3), narrative summary Observation,
AllergyIntolerance, and a **Provenance resource carrying the clinician's e-signature**.

> **Use the Provenance resource in your pitch.** FHIR has a native `Provenance` type with
> `agent` (who did what) and `signature` (ISO "Verification Signature"). That means your
> 21 CFR Part 11 e-signature and ALCOA+ attribution aren't bolted on — they're expressed
> in the standard's own vocabulary. Almost no hackathon team will know this exists.

## How to link it up

### 1. Environment variables (`.env` — never commit real keys)
```bash
FHIR_MODE=hapi                                   # hapi | epic
FHIR_BASE_URL=https://hapi.fhir.org/baseR4       # swap for Epic sandbox base URL in epic mode
FHIR_PATIENT_ID=synthetic-maria-gonzalez         # in epic mode: a real Epic sandbox patient ID
# Epic mode only:
EPIC_CLIENT_ID=
EPIC_TOKEN_URL=
```

### 2. Seed the patient (hapi mode only, run once)
```bash
curl -X PUT "$FHIR_BASE_URL/Patient/synthetic-maria-gonzalez" \
  -H "Content-Type: application/fhir+json" \
  -d @data/patients/synthetic-maria-gonzalez.json
```
(`PUT` with the id lets you control the patient ID; `POST` would let the server assign one.)

### 3. Fill the template and POST the bundle
The template uses `{{PLACEHOLDERS}}`. Your `fhir_writer` module replaces them:

| Placeholder | Filled with |
|---|---|
| `{{PATIENT_ID}}` | `FHIR_PATIENT_ID` |
| `{{TIMESTAMP}}` | ISO-8601 UTC at signing time |
| `{{ENGLISH_SUMMARY}}` | `english_summary` from the structurer output |
| `{{SIGNER_NAME}}` | clinician name captured at e-signature |
| `{{SIGNATURE_DATA_BASE64}}` | base64 of the signature payload |

Then POST the whole bundle to the base URL:
```bash
curl -X POST "$FHIR_BASE_URL" \
  -H "Content-Type: application/fhir+json" \
  -d @filled_bundle.json
```
A transaction bundle posts to the **base URL**, not to a resource path — the `request`
block inside each entry tells the server where each resource goes.

### 4. Add this to your `fhir_writer` PDD prompt
```
Read the transaction Bundle template at data/fhir/intake_bundle_template.json and
replace the placeholders {{PATIENT_ID}}, {{TIMESTAMP}}, {{ENGLISH_SUMMARY}},
{{SIGNER_NAME}}, and {{SIGNATURE_DATA_BASE64}} with values from the signed intake record.
POST the filled bundle to the base URL in FHIR_BASE_URL. Support two modes via FHIR_MODE:
"hapi" (no auth) and "epic" (SMART on FHIR OAuth 2.0 bearer token). Return the created
resource IDs. Use only synthetic or sandbox test data.
```

### 5. Verify the write landed
```bash
curl "$FHIR_BASE_URL/Observation?subject=Patient/$FHIR_PATIENT_ID&_sort=-_lastUpdated"
```
Show this in the demo — proof the record actually reached the server.

## Compliance note for the README
> All data in this repository is synthetic. The Patient resource is tagged `HTEST`
> (test health data) and no real PHI is processed. FHIR writes target a public test
> server or Epic's synthetic sandbox. This project demonstrates compliance *controls*
> (Part 11 e-signature via FHIR Provenance, ALCOA+ audit trail, source-word fidelity),
> not a production HIPAA deployment.
